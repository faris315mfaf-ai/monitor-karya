Monitor Karya di ponsel untuk model subholding

Rancangan agar empat peran baru (Admin subholding, Supervisor, Superuser, Manajemen) bekerja nyaman dan andal di ponsel: cepat di jaringan seluler, bisa memotret bukti langsung, tetap bisa melapor saat sinyal hilang.

Keputusan yang diusulkan

Fase 1 · 2 hariOptimalkan web (PWA) untuk semua peranJalan di Android dan iPhone tanpa pasang aplikasi. Kompresi foto, kamera langsung, pasang ke layar utama.

Kondisi sekarang

Yang sudah berjalan

  • Web responsif. Semua layar subholding punya tata letak ponsel: navigasi bawah di bawah 600px, pop-up menjadi lembar dari bawah, kartu satu kolom.
  • PWA dasar. public/manifest.webmanifest, public/sw.js (daring-duluan, halaman /luring.html saat tidak ada sinyal), ikon maskable.
  • Server siap untuk klien ponsel. Unggah bukti menerima header Idempotency-Key (aman diulang saat sinyal putus), URL foto bertanda tangan bisa diminta berkelompok lewat POST /api/evidence/signed (maks 60 per permintaan).
  • Fondasi Android. 396 berkas Kotlin: Compose + Hilt + Retrofit + Room, cookie sesi terenkripsi, antrean luring (AntreanOutbox, OutboxProsesor, KunciIdempotensi), sistem desain mk-Compose, uji E2E di emulator.

Celah yang harus ditutup

  • Android masih model lama. RoleTabs.kt hanya mengenal PIC, Kepala divisi, Admin PT, dan seterusnya. Akun Admin subholding, Supervisor, dan Superuser yang masuk lewat APK sekarang tidak punya tab yang benar.
  • Foto dikirim utuh. Pemilih bukti di src/components/views/sh-admin/ mengunggah berkas asli (foto ponsel 3–8 MB). Di 4G pinggiran satu laporan berfoto tiga bisa makan lebih dari satu menit dan sering gagal di tengah jalan.
  • Manifest PWA usang. Deskripsi dan pintasan masih "Laporan harian" dan "Log aktivitas" milik model lama.
  • Thumbnail berat. Dashboard Superuser memuat foto berukuran penuh untuk kotak 44px. Belum ada versi kecil di sisi server.
  • Tidak ada notifikasi dorong. Admin subholding baru tahu laporannya diminta perbaikan saat membuka Kotak masuk.

Alur lapor saat sinyal putus

Alur ini inti Fase 2 (Android) dan versi ringannya di Fase 1 (draf web). Kuncinya: laporan dan setiap foto punya kunci idempotensi sejak dibuat di ponsel, jadi pengiriman ulang tidak pernah membuat laporan ganda.

Fase 1 · Web dan PWA

Foto dan unggah

  • Kompresi di peramban sebelum unggah: sisi terpanjang 1600px, JPEG kualitas 0,8, orientasi EXIF dibakar ke gambar lalu metadata dibuang (lokasi GPS ikut hilang). Target ≤ 600 KB per foto. Tempat: modul baru src/lib/image-compress.ts, dipakai sh-admin/bukti-picker.
  • Input kamera: accept="image/*" capture="environment" untuk tombol "Ambil foto"; tombol galeri tetap terpisah.
  • Unggah paralel maks 2, progres per foto, tombol "Coba lagi" per foto, header Idempotency-Key per foto (sudah didukung server).
  • Draf formulir disimpan di IndexedDB per perangkat (bukan di server) sehingga tab tertutup atau sinyal putus tidak menghapus isian.

Tampilan

  • Area aman iPhone: navigasi bawah dan tombol yang menempel memakai env(safe-area-inset-bottom); tinggi lembar memakai dvh (sudah) dan tidak tertutup keyboard (interactive-widget=resizes-content di meta viewport).
  • Input 16px ke atas agar Safari tidak memperbesar halaman saat fokus; target sentuh ≥ 44px (sudah di layar baru, periksa layar lama yang masih dipakai Superadmin).
  • Tarik untuk memuat ulang di Dashboard dan Kotak masuk; daftar panjang Riwayat dimuat bertahap (20 per halaman, sudah didukung API).
  • Strip foto di pop-up: sembunyikan bilah gulir horizontal, tambahkan scroll-snap.

PWA

  • Perbarui manifest.webmanifest: deskripsi model subholding, pintasan "Tambah laporan" (Admin) dan "Persetujuan" (Supervisor), theme_color mengikuti tema.
  • Service worker: simpan aset statis versi build (JS, CSS, font) dengan strategi cache-duluan; data API tetap tidak disimpan (kebijakan SW v2: tidak menyimpan data pribadi).
  • Ajakan "Pasang ke layar utama" sekali, setelah laporan pertama berhasil dikirim.

Server pendukung

  • Thumbnail: saat unggah, buat versi 320px (WebP) dan simpan berdampingan; POST /api/evidence/signed menerima { ids, size: 'thumb' | 'full' }. Dashboard memakai thumb, lightbox memakai full.
  • Header cache untuk URL bertanda tangan (berlaku 5 menit) agar gambar yang sama tidak diunduh ulang selama sesi.

Fase 2 · Android native

Modul

  • :feature:subholding-admin (baru): Dashboard (form + daftar hari ini), Kotak masuk, Riwayat.
  • :feature:persetujuan (ditulis ulang): antrean Supervisor, keputusan, komentar.
  • :feature:ringkasan-subholding (baru): dashboard Superuser & Manajemen.
  • Modul lama (proyek, eskalasi, entitas, ringkasangrup, audit, layar mejakadiv, mingguan, penerimaan) dikeluarkan dari navigasi, kodenya diarsipkan di cabang agar APK lebih kecil.
  • RoleTabs.kt mengikuti ROLE_TABS web baru; peran tak dikenal menampilkan layar "Peran ini belum tersedia di aplikasi, buka versi web" dengan tautan, bukan layar kosong.

Data lokal (Room)

  • sh_options (PT, pelapor terakhir), sh_report_cache (daftar hari ini + riwayat terakhir), sh_outbox (laporan antre + status), sh_outbox_file (berkas foto terkompresi di penyimpanan aplikasi, dihapus setelah terkirim).
  • Migrasi Room baru menambah tabel; tabel model lama dibuang saat versi naik (data lama hanya cache).

Foto

  • Kamera lewat ActivityResultContracts.TakePicture, pilihan galeri lewat Photo Picker (tanpa izin penyimpanan).
  • Kompresi 1600px JPEG 80, EXIF dibuang kecuali orientasi yang dibakar; hasil disimpan sebelum laporan masuk antrean.

Notifikasi

  • Tanpa layanan tambahan: WorkManager berkala tiap 30 menit memeriksa /api/sh/inbox dan memunculkan notifikasi "Laporan diminta perbaikan" atau "Laporan disetujui".
  • Opsional: notifikasi dorong instan lewat FCM. Butuh proyek Firebase dan endpoint pendaftaran token di server.

Keamanan

  • Sesi tetap cookie mk_session; di Android disimpan terenkripsi (sudah). Keluar menghapus antrean yang belum terkirim hanya setelah konfirmasi, karena berisi kerja pelapor.
  • Akun admin subholding dipakai bersama: aplikasi tidak menyimpan sandi; kunci layar perangkat disarankan, buka dengan sidik jari opsional.
  • Foto di penyimpanan aplikasi (bukan galeri publik), dihapus setelah terkirim. Metadata lokasi dibuang.
  • URL foto bertanda tangan berlaku 5 menit dan tidak disimpan di luar cache gambar.

Pengujian dan kriteria selesai

  • Vitest untuk kompresi gambar (ukuran, orientasi, metadata hilang) dan antrean draf web.
  • Uji unit Android: RoleTabs baru, pemetaan DTO /api/sh/*, prosesor antrean (idempotensi, urutan laporan sebelum foto, coba ulang).
  • E2E emulator (lingkungan yang sudah ada: DB 54329, MinIO 59000, server dev 3100): lapor dengan mode pesawat → aktifkan jaringan → laporan dan 3 foto terkirim sekali, tidak ganda.
  • Uji perangkat nyata: satu Android kelas bawah (Android 8/9), satu iPhone dengan Safari dan PWA terpasang.
  • Selesai bila keempat peran bisa menyelesaikan alurnya di ponsel tanpa perlu membuka desktop, dan anggaran kinerja di atas terpenuhi.

Yang perlu diputuskan pemilik

  1. Distribusi Android: Google Play (uji internal lalu publik) atau APK langsung dibagikan ke admin subholding.
  2. Notifikasi instan: cukup pemeriksaan berkala 30 menit, atau siapkan Firebase (FCM) untuk notifikasi saat itu juga.
  3. iPhone: cukup PWA, atau perlu aplikasi iOS di kemudian hari.
  4. Luring untuk Supervisor: diusulkan tidak (keputusan butuh data terbaru); konfirmasi.
Catatan risiko. Selama Fase 2 belum rilis, siapa pun yang masih memakai APK lama dengan akun peran baru akan melihat aplikasi yang tidak sesuai. Langkah Hari 0 menutup risiko ini dan sebaiknya dikerjakan lebih dulu.
